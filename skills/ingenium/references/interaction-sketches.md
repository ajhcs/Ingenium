# Connected wireframes as iterative definition

Use this for consequential interaction choices in an application, agent tool, engineering workbench or workflow. Small text corrections and settled component edits don't need a new study. Ingenium stays usable on its own: the model-specific obligations below apply only when the task is model-backed. Respect the person's scope, authorization and withheld references.

## What the person will look for

- One representative connected path that resolves a real uncertainty, shown early, before you expand into every workflow.
- Behavior they can inspect: what each control does, what's draft versus applied versus persisted, and how to recover from a refusal or mistake.
- Evidence about behavior that matches its source: exercised interactions reported as exercised, static ones as specified or untested.
- Where a model is involved, a two-way match between the interface and the model's purposes, requirements and acceptance procedures.

## Ground a small connected path

Look at relevant professional tools and actual UI precedents before drawing; reuse evidence you already inspected when it fits. Note the source, what you observed, the proposed adaptation and its limits, and whether you saw it directly (screenshot, interaction) or through documentation or a routed finding. A source you couldn't access is a limit, not evidence. References inform choices; they don't demand feature parity or permit copying assets. If the work involves several independent precedents to survey, use subagents as needed.

Start promptly with one connected path that resolves a material uncertainty, using authorized representative content and enough states to show the action and its outcome. A field catalog alone isn't a user interface, and disconnected specification cards don't demonstrate a workflow. Where they affect the interaction, show the workspace, navigation, selection, relevant tools and context in a plain low-fidelity interface. Keep model or API annotations beside the interface rather than over it. Keep the source editable and inspect the rendered pixels at the intended size.

## Make behavior inspectable

Expose the relevant fields, options, selection sources, free-entry rules, defaults, unknowns, actions, state transitions and side effects. Where those boundaries exist, show before, local draft, applied change and persisted result. Cover validation, refusal, correction, cancel, undo and recovery along the selected path, and label any route you didn't render or execute. An action label doesn't prove a successful save, a restored state or a complete workflow.

Where guidance, canvas and detail views share information, say who owns the values and the selection. Show the linkage without inventing duplicate records or requiring duplicate entry. Layout and disclosure choices remain proposals until reviewed. A polished sketch or existing implementation doesn't imply an edit lock, forced sequence, commit gesture or save-before-navigation rule. Keep free movement when requested and name unresolved tensions.

Choose controls from purpose and data semantics. A slider, dropdown, palette or drag gesture is an option, not a requirement because someone mentioned it. Precise quantities need meaningful units, bounds and resolution. Stable references differ from copied labels; proximity, lines and frames don't establish connectivity, ownership or containment. A diagram of a target system doesn't authorize operating it.

**Interactive demos:** exercise the actual controls, keyboard and focus behavior, collapse and return, selection synchronization and resizing. Record the state, command or gesture, the observed result and the limits; screenshots alone don't prove these. For a static wireframe, report them as specified or untested. Deliver only the requested artifact types; a raster export doesn't replace editable source.

**Animated interactions:** separate model/action state from visual progress. Say how input during a transition is handled (retarget, queue or ignore) and exercise rapid reversal and repeated input against that policy, including from an intermediate visual state. Focus and action availability follow the task's actual policy; visual completion isn't model completion or persistence. Check the reduced-motion path for the same task. Use [Media and delivery context](delivery-context.md) for continuous playback and export evidence.

## Reconcile the model and the interface

For a model-backed task, identify the authoritative source and map displayed states and interactive elements, through stable IDs or resolvable anchors, to their purpose, requirements, model properties, typed data or commands, constraints and acceptance procedures. Keep natively supported behavior, new model/API proposals and unknown semantics distinct. Current API limits qualify implementation evidence; they don't silently become product requirements.

Check both directions within a stated scope: every displayed action has a model purpose and binding, and every required in-scope action or state has a UI or a justified external route. Each in-scope requirement also needs a realization and acceptance procedure, or an explicit gap; matching every control doesn't establish requirement coverage. Include disabled and modal availability, and distinguish proposed feedback from an executed validation receipt. Mark omissions, deferred workflows and unsupported persistence. Don't invent a widget for every internal field or require one screen per scenario step. Parser success, a projected graph or a trace matrix is bounded evidence, not proof of semantics, behavior or acceptance.

Review the pixels and the model/action coverage independently when warranted and possible. Feed findings back into needs, requirements, model semantics, data contracts, constraints and acceptance checks, then redraw and recheck what changed. Bind every check receipt to the exact model/source revision, sketch/view revision and inputs it inspected; an earlier pass doesn't qualify edited artifacts. When definitions conflict, reconcile them instead of polishing over the gap.

## Done when

Stop at the agreed review boundary: the first useful connected study is in front of the person, their feedback gate and earlier versions are intact, and you haven't expanded past what they authorized. Approval of a visual kind doesn't settle every layout, behavior or product decision. Continue already authorized work without inventing new approval rituals, and don't read a design review as implementation authorization.

The handoff names the representative path, editable and rendered outputs, source/requirement bindings, assumptions and questions, observed versus planned checks, coverage limits and the safest next review. A sketch is a proposal until accepted; it doesn't establish implementation, full accessibility, conformance or engineering adequacy. Source changes, a reviewed merge, packaged guidance and deployment into an installed client are separate outcomes, and this guidance grants no publication, installation or production authority.
