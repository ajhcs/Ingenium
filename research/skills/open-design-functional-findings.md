# Open Design: functional skill research

Source: [`nexu-io/open-design`](https://github.com/nexu-io/open-design/tree/8d820a698908dc279ef3d5aeb4ce6d156211a499), commit `8d820a698908dc279ef3d5aeb4ce6d156211a499`, retrieved 2026-10-21. Ingenium comparison baseline: `f70db6171196c2c4452bc53eb24e82ba7cad5d9c`. This is source analysis, not an executed evaluation of either project.

## Coverage and what the counts mean

The pinned checkout contains **549 actual `SKILL.md` paths and 461 exact SHA-256 contents**, including templates, plugin bundles, examples, test fixtures and tools. Those counts do not mean 549 independent methods. The team divided the source into 169 functional-root skills, 302 design-template/official-example skills, and 78 remaining plugin/fixture/example skills. The 302 partition is **115 `design-templates` + 187 `plugins/_official/examples`**. An initial directory-index grouping counted 199 examples by also including 12 `plugins/spec/examples`; the inventory and final partition use exact prefixes.

The completed functional partition contains **169 paths**: this reader covered 145 and the additional reader directly covered 24:

- **60 complete bodies read directly**, including command examples, output requirements, constraints and negative guidance. `open-design-functional-read-log.json` names every one.
- **85 catalogue entries read by an explicit transformed method**: all 18 complete normalized body variants, all per-entry frontmatter and source/description values, and both custom additions (`creative-director`, `ui-ux-pro-max`) directly in full. This is not an exact-byte duplicate assertion. The normalizer verifies **85/85 exact body reconstructions** from the normalized body and complete variable values; per-file source/frontmatter/normalized-body hashes are retained in `open-design-audit.mjs` and `open-design-stub-read-evidence.json`. The `What it does` description matched the frontmatter in 83/85; the other two contain the custom sections just noted and were separately read in full. Unicode frontmatter was reread with UTF-8 console output after detecting Windows console substitution.
- **24 complete large functional bodies directly read by the extra reader**, with all 24 source hashes matching the parent inventory. The exact per-file evidence is `open-design-extra-reader-mui/functional24-read-evidence.json`; its analysis is `FINDINGS.md`. This is an additional reader's completed evidence, not a claim that this reader personally read those 24 raw bodies.

`open-design-functional-support-inventory.csv` inventories **279 text/source/license sidecars** under `skills/`, including files not directly linked. This includes five `.tsx` files from linked Remotion templates that were added in a corrective inventory pass; it is a superset of local text operational references, not a claim all were semantically reviewed. This reader fully read the functional directory guide/README and two operational references (`research-decision-room/references/evidence-model.md`, `reference-design-contract/references/checklist.md`); selected notices are separately recorded. The extra reader inventories 124 support files in its partition and records nine full reads, including selected notices, `ui-animation` source/decision references and `oil-motion/references/runtime.md`. The merged functional support inventory records **15 full reads and 264 inventoried-not-read**, including all five `.tsx` files unread. No upstream script was run. Six PNG files and one `.gitignore` are outside this text/source inventory; images, fonts, video binaries and full application implementation are outside the semantic-reading claim. Runtime-selected `DESIGN.md`, user paths and external upstream bundles are not locally resolved operational files.

The source itself explains that many curated entries are lightweight stubs, not vendored upstream workflows (`skills/AGENTS.md`, “Curated design / creative catalogue”). In particular, `skills/ui-ux-pro-max/SKILL.md` explicitly says its CSV/search/templates are not bundled. An advertised capability, name or upstream link is not evidence that the capability exists locally. A stub's claim to be an “OpenAI production frontend playbook” is a third-party description; this study did not treat it as documented OpenAI guidance or fetch that unpinned upstream bundle.

Baseline material read for comparison: the Ingenium skill; `composition`, `checks`, `interaction-sketches`, `record-contract`, `assets`, `fonts`, `resource-libraries`, `ui`, `design-methods`, `methods/fontplate`, and `methods/element-collage`. Those already cover much of what upstream calls design quality: purpose, representative content, explicit choices, exact source identities, actual rendering, native controls, state/recovery paths, scoped checks, licensing and honest uncertainty. The following are incremental opportunities, not claims Ingenium lacks those foundations.

## Source/license evidence and copying boundary

`LICENSE` is Apache-2.0 with “Copyright 2026 Open Design contributors.” `skills/README.md` expressly states skills are Apache-2.0 **unless their own license says otherwise**. The functional sidecar inventory includes all located nested notice files with byte hashes. Exact notices directly inspected in this lane include root `LICENSE`, `skills/frontend-design/LICENSE.txt` (Apache-2.0), `skills/soft-skill/LICENSE` (MIT, Leonxlnx 2026), and `skills/web-clone/LICENSE` (MIT, Jane / @xiaoerzhan / 小耳 2026). Other nested notices remain indexed, not blanket-approved; the extra reader owns its own license evidence.

For redistribution of copied Apache material, the actual terms include distributing the license, retaining applicable notices, marking modified files, and retaining applicable NOTICE contents if supplied; nested MIT requires the copyright and permission notice with copies/substantial portions. A README mention alone does not satisfy those texts. These are observations of the included notices, not legal clearance for all assets or brands. No new external service terms were accepted. No credentials, optional tools, billed API or upstream scripts were used.

This research delivers original analysis plus source identities and hashes. It does **not** deliver upstream code, copied templates, fonts, images, full skill text or generated assets. If the integrator later copies a passage or implementation, it must review that exact selected file's notice and any embedded third-party source rather than rely on the repository-wide license headline.

## Suggested synthesis shape

The lowest-cost useful result is a few optional task routes: **reference adaptation**, **qualitative design evidence**, **delivery-context checks**, plus a small **export failure** diagnostic. Media jobs and subject identity can be compact conditional notes rather than new infrastructure. Preserve all eight Ingenium methods and native/model traceability. Keep ordinary prose sufficient; no mandatory tables, file trios, score systems, fixed ordering, provider commands or hidden gates. These are implementation suggestions for the synthesis owner, not product changes made in this branch.

The study only establishes what the pinned sources say and where the baseline overlaps. It has not measured whether the proposed additions improve outcomes. Designed examples would need to be labeled designed examples; observed evaluation would require an actual representative task and evidence, including what changed and what remains uncertain. No claim about future intelligence scaling follows from a source meta-analysis.
